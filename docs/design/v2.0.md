# PixelPilot v2.0 設計方針

> ステータス: Draft(方針合意済み・詳細設計前)
>
> ライセンス / 配布: OSS として公開する(料金体系は現時点で設けない)。Firebase App Distribution と GitHub Releases で配布する(v2.0 はデバッグ版の App Distribution のみ。リリース版はバックログ #106)
>
> v2.0 の範囲: **v1.0 Android アプリの置き換え(MVP)**。それ以外は v2.x 以降で対応する(4. 機能範囲)
>
> 詳細設計: [Standard(Android 単体)](./v2.0-standard.md)

## 1. 背景

v1.0(2025-05)は Android 単体で Bluetooth HID マウスとして振る舞う最小実装だった。
接続先のハードコード、初期化タイミング、接続状態の不可視、機能不足(スクロール・キーボード無し)などの課題があり、
v2.0 では対象 OS・接続方式から設計を見直す。

## 2. プロダクトの基本方針

- **基本はモバイルアプリ単体**。HID プロトコルでマウス・キーボードの振る舞いを再現し、ホスト側にソフトのインストールを求めない。
- **デスクトップ版は高機能版**。OS 側での処理(アプリ起動・スクリプト・状態取得など)が必要な機能や、HID 直結できない端末のためにのみ使う。
- ユーザーの手間を最小化することを優先する。

## 3. 対象プラットフォーム

| 区分 | 対象 | サポート |
|---|---|---|
| クライアント | Android | 公式 |
| クライアント | iOS | 公式(デスクトップ版の接続が前提) |
| ホスト / デスクトップ版 | Windows, macOS | 公式 |
| ホスト / デスクトップ版 | Linux, ChromeOS, iPadOS など | ベストエフォート |

v2.0 で提供するのは Android クライアントのみ。iOS 版・デスクトップ版は v2.x 以降で提供する。

### iOS が HID 直結できない理由

- Bluetooth Classic: アプリから HID Device プロファイルを扱う公開 API が無い(Android の `BluetoothHidDevice` 相当が無い)。
- BLE: `CBPeripheralManager` で HID サービス(0x1812)を公開できない。バックグラウンドでのアドバタイズも制限される。
- USB: アプリが USB ガジェットとして振る舞う手段が無い。

そのため iOS 版は、デスクトップ版に接続して入力を代行してもらう形で提供する。

## 4. 機能範囲

### Standard(モバイル単体・Bluetooth HID)

v2.0 は v1.0 Android アプリの置き換え(MVP)とし、マウスとキーボードに絞る。詳細は [Standard 詳細設計 1. 範囲](./v2.0-standard.md#1-範囲)。

| 機能 | 提供時期 |
|---|---|
| マウス(移動、クリック、スクロール、ドラッグ) | v2.0 |
| キーボード | v2.0 |
| メディアキー(Consumer Control) | v2.x |
| ショートカットパッド(キー組み合わせ・キー列の送信。Stream Deck ライク) | v2.x |

### デスクトップ版で追加される機能

- アプリ起動・スクリプト実行
- ホスト状態の反映(ミュート状態、アクティブアプリに応じたボタン切り替え等)
- 任意文字(Unicode / 日本語)入力
- クリップボード共有
- HID 直結できない端末(iOS など)への入力代行

## 5. 接続方式

| 経路 | 用途 | デスクトップ版 |
|---|---|---|
| Bluetooth Classic HID | Android → ホストへ入力を直接送る | 不要 |
| LAN(Wi-Fi) | クライアント ↔ デスクトップ版 | 必要 |
| USB(Android: AOA / iOS: usbmux) | クライアント ↔ デスクトップ版 | 必要 |

### USB について

- 非 root の Android は USB HID ガジェットになれない(ガジェット構成の変更にはシステム権限が必要)。
- `android.hardware.usb` の Accessory モード(`UsbManager.openAccessory()`)で、AOA プロトコルを話すデスクトップ版と通信する。
  PC からは HID ではなくベンダー固有デバイスとして見えるため、デスクトップ版が必須。
- iOS は usbmux 経由(iOS アプリはソケットで待ち受け、デスクトップ版が usbmux で接続)。
- Windows の AOA は WinUSB ドライバの割り当てが必要(インストーラで自動化する)。

## 6. デスクトップ版の役割切り替え

接続時のハンドシェイクで、クライアントが**能力**を申告する。OS 名ではなく能力で役割を決める。

```
Client → Desktop: Hello { platform: ANDROID, hidDirect: true,  ... }
Client → Desktop: Hello { platform: IOS,     hidDirect: false, ... }
```

| hidDirect | 入力の経路 | デスクトップ版の役割 |
|---|---|---|
| true | Bluetooth HID でホストへ直接(デスクトップ版を通さない) | 高機能版の機能のみ |
| false | デスクトップ版経由(LAN / USB) | 入力代行 + 高機能版の機能 |

- HID 直結時は入力経路にデスクトップ版を挟まないため、遅延が増えない。
- HID プロファイルが無効化された Android 端末も `hidDirect: false` として iOS と同じ経路で動作する。

## 7. アーキテクチャ

### 方針: 部品は共通、骨格は分離

Kotlin Multiplatform / Compose Multiplatform を使う。

- **共通化**: 入力イベント、ショートカット定義、プロトコル、マウス・キーボード・ショートカットパッドの UI 部品
- **プラットフォーム別**: 画面遷移、ホスト選択・ペアリング案内、接続フロー

共通コードに `isIOS` のような分岐を持ち込まない。

### デスクトップ版が必須かどうかは利用可能な経路から導く

```kotlin
// commonMain
enum class TransportKind { BLUETOOTH_HID, AGENT_LAN, AGENT_USB }

interface PlatformTransports {
    val available: StateFlow<List<TransportKind>> // 実行時に判定。HID プロファイルの確認が済むと変わる
}

val List<TransportKind>.requiresDesktop: Boolean
    get() = TransportKind.BLUETOOTH_HID !in this
```

- Android: 端末が Bluetooth を備えていれば `BLUETOOTH_HID` を含め、HID Device プロファイルが使えないと分かった時点で外す
- iOS: `AGENT_LAN`, `AGENT_USB` のみ

### 入力イベントの共通表現

入力は **HID Usage コード**(キーコード、ボタン、ホイール)で表現する。

- Bluetooth HID 経路: そのまま HID レポートに変換して送信
- デスクトップ版経路: デスクトップ版が OS の入力 API(Windows `SendInput` / macOS `CGEvent`)に変換

### モジュール構成

**model / domain / view のレイヤー**で分け、各レイヤーの中を機能ごとのモジュールに分ける。経路の実装は `transport/` に置く。

```
model/                データ型のみ                                              … commonMain
  input/              InputEvent、HID Usage 定数
  connection/         TransportKind、HostDevice、ConnectionState、ErrorReason
  settings/           ホストの OS・キーボード配列の種類、マウスの設定、アプリの設定
  shortcut/           (v2.x)ショートカットのデータモデル
domain/               ロジックとインターフェース                                … commonMain
  input/              TouchpadInterpreter、KeyboardLayout(US / JIS)
  hid/                Report Descriptor、HidReportEncoder
  transport/          InputTransport、PlatformTransports(インターフェース)
  settings/           設定・前回のホストのリポジトリ(インターフェース)
  protocol/           (v2.x)デスクトップ版とのプロトコル
view/                 Compose Multiplatform の UI(iOS 版と共有)                … commonMain
  common/             テーマ、共通部品(接続状態の表示など)、文字列リソース
  mouse/              マウス画面
  keyboard/           キーボード画面
  shortcut/, media/   (v2.x)
transport/            経路の実装(domain/transport のインターフェースを実装)
  bluetooth-hid/      BluetoothHidDevice                                         … androidMain
  agent/              (v2.x)デスクトップ版との通信(LAN)                         … commonMain
  usb-aoa/            (v2.x)android.hardware.usb の Accessory モード             … androidMain
  usbmux/             (v2.x)待ち受けソケット                                      … iosMain
androidApp/           骨格: 画面遷移・メインのタブ・ホスト選択・設定画面・Koin の組み立て・設定の保存(DataStore)
iosApp/               (v2.x)SwiftUI の骨格 + Compose 部品(ComposeUIViewController)
desktopApp/           (v2.x)エージェント(役割切り替え・入力注入・高機能版の機能)
build-logic/          各モジュール共通のビルド設定(convention plugin)
```

依存のルール:

- 依存の向きは **view → domain → model** のみ。`transport/*` は domain と model に依存し、各アプリ(`androidApp` など)がすべてをつなぐ。
- **view は transport に依存しない。** 経路は `domain/transport` のインターフェース越しに使い、実装はアプリが Koin で注入する。
- **同じレイヤーの中で横の依存は作らない**(例: `view/mouse` は `view/keyboard` に依存しない)。共有するものは `*/common` に置く。例外として model 同士の依存は認める。
- `*/common` は、2 つ以上のモジュールで共有するものが出てから作る。v2.0 では `view/common` のみ。
- ホスト選択・設定画面・メインのタブは画面遷移・接続フローの一部(骨格)のため、`view/*` ではなく各アプリに置く。

Gradle のプロジェクト名は「レイヤー-機能」(`:model-input`、`:transport-bluetooth-hid` など)とする。`model/input` と `domain/input` のようにディレクトリ名が重なるため、Kotlin のモジュール名の衝突を避ける。

### HID デバイス構成

マウス・キーボード・Consumer Control の複合デバイス(Report ID で区別)。

- マウス: 5 ボタン(左・右・中・戻る・進む)、X/Y、縦ホイール、横スクロール(AC Pan)
- キーボード: 修飾キー + 通常キー
- Consumer Control: 音量・再生制御など

## 8. 注意事項

- **キーボード配列**: HID は物理キー位置を送るため、ホストの配列(JIS / US)で記号の出方が変わる。Standard ではホスト配列を設定で選択させる。日本語などの任意文字入力はデスクトップ版の機能とする。
- **修飾キー**: Windows と macOS で Ctrl / ⌘ が異なる。ショートカット定義はホスト OS ごとに持てるようにする。
- **OS 権限**:
  - macOS: デスクトップ版にアクセシビリティ権限が必要
  - Windows: 管理者権限のウィンドウには通常権限から入力を注入できない(UIPI)
  - iOS: ローカルネットワーク利用許可(Bonjour での発見時)
  - Linux: Wayland 環境での入力注入は困難(ベストエフォート)

## 9. 決定事項

### 9.1 デスクトップ版との通信路の優先順位

**USB > Bluetooth > LAN** の順に優先し、利用可能な最上位の経路を自動選択する。

| 経路 | Android | iOS | 備考 |
|---|---|---|---|
| USB | AOA(`android.hardware.usb`) | usbmux | 遅延・ジッターが最小 |
| Bluetooth | RFCOMM 独自チャネル(HID と並行) | BLE GATT 独自サービス(要検証) | デスクトップ側はネイティブ API 連携が必要(Windows: WinRT, macOS: IOBluetooth / CoreBluetooth) |
| LAN | TCP / WebSocket | TCP / WebSocket | 9.3 参照 |

### 9.2 DI

- Dagger / Hilt は KMP で使えないため不採用。
  - Dagger は JVM 向けの jar のみを配布しており(2.60.1 時点で Gradle Module Metadata なし)、Kotlin/Native(iOS)向けの成果物が無い。`commonMain` / `iosMain` から依存できない。
  - Hilt は Android 専用(`Application` / `Activity` 前提の aar)。
  - Android だけ Hilt、共通部分を別 DI にすると DI が二重になり保守性が悪い。
- **Koin を採用する**(KMP 対応、Compose Multiplatform 向けの統合あり)。
- 使い方(7. モジュール構成のレイヤーとの対応):
  - **model・domain は Koin に依存しない。** 依存はコンストラクタで受け取る普通のクラスにし、DI の仕組みを知らないまま単体テストできるようにする。
  - **view・transport の各モジュールは、自分の Koin モジュールを `di` パッケージに置く**(例: `transport/bluetooth-hid` が `PlatformTransports` の実装を束縛する、`view/mouse` が画面の状態を持つクラスと、それが使う domain のクラスを定義する)。view は `koin-compose` で受け取る。
  - **各アプリ(`androidApp` など)が、すべての Koin モジュールを並べて起動する**(`startKoin`)。プラットフォーム固有の実装(DataStore による設定の保存など)の束縛もアプリに置く。
  - Koin の定義の解決漏れは、アプリの単体テスト(`verify()`)で検出する。
- 参考: コンパイル時検証が欲しくなった場合の KMP 対応候補として Metro(Dagger 風 API のコンパイラプラグイン)、kotlin-inject がある。

### 9.3 LAN 接続

ルーターを介さないピアツーピア接続(Wi-Fi Direct)は **v2.0 では見送る**。

- 利用できる組み合わせ:
  - Android ↔ Windows: 可(Android `WifiP2pManager` / Windows WinRT `Windows.Devices.WiFiDirect`。アダプタ・ドライバ依存)
  - Android ↔ Linux: `wpa_supplicant` の P2P で可(ベストエフォート)
  - Android ↔ macOS: 不可(macOS は Wi-Fi Direct を一般アプリに提供していない)
  - iOS ↔ 全て: 不可(iOS は Wi-Fi Direct 非対応。Apple 端末間の AWDL / MultipeerConnectivity のみ)
- 見送る理由:
  - ルーターが無い環境のニーズは、優先度の高い USB / Bluetooth で満たせる。
  - 公式サポート対象のうち効果があるのは Android ↔ Windows のみ。
  - 権限(Android 13 以降の `NEARBY_WIFI_DEVICES`)、接続ごとの確認ダイアログ、端末によっては通常の Wi-Fi 接続が切れるなど、UX と実装のコストが大きい。
- v2.x 以降で、Android ↔ Windows 向けの LAN 経路の拡張として再検討する余地はある。

そのため **同一 LAN 内での直接 TCP 接続 + mDNS(DNS-SD)による自動発見** を採用する。中継サーバーは使わない。

- **待ち受け側はデスクトップ版**(v1-alpha と同じくデスクトップ版をサーバーとする)。常時起動していて安定しているため。
- 発見: デスクトップ版が `_pixelpilot._tcp` をアドバタイズし、モバイルが探索する(Android: `NsdManager`、iOS: Bonjour(`NSBonjourServices` / `NSLocalNetworkUsageDescription` が必要)、デスクトップ: JmDNS 等)。
- 初回ペアリング: デスクトップ版に QR コードを表示し、接続先・公開鍵・ワンタイムトークンを渡す。mDNS が使えないネットワーク向けに、QR の接続先で直接接続するフォールバックも兼ねる。
- 暗号化: ペアリング時に交換した鍵をピン留めした TLS(または Noise プロトコル)。詳細は別途設計する。
